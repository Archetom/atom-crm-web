# 功能行为对齐：后端契约需求

本文件记录参考交互中前端不能安全猜测、且尚需要跨仓库能力的部分。已落地的契约保留在对应章节，避免把已完成闭环误列为后端缺口；在契约未到位前，应用不以静态数据或未授权调用伪造完成状态。

## 1. 客户列表场景、筛选、排序、列与批量操作

- 已实现：客户查询和导出均已支持服务端裁决的下属负责人、保存/临时高级筛选、静态及目录确认的动态排序、字段布局、关键词和分页；客户公海已另行提供版本化批量领取、分配和删除。浏览器只提交已发布 request 字段，最终范围、字段策略与动作资格均由服务端重判。
- 查重边界：Web 现以既有 `POST /api/v1/customers/duplicate-check` 支持名称或 E.164 联系电话的当前可见范围布尔查重。参考站可见的查重方式切换与“跨业务线”选项尚无安全契约；后端如需支持，必须具名发布可选方式、跨范围资格及仍只返回布尔结果的 schema，不能由浏览器传入业务线、成员或数据范围。
- 仍需新契约：若要对齐“跨业务线”查重，服务端必须发布受限的查重方式与资格，且仍只返回当前可见范围的布尔结果；浏览器不能提交业务线、成员或数据范围。

## 2. 线索、联系人下属范围、动态筛选与列偏好（已实现）

- 已实现：线索的已转化、本人/下属/关注场景与联系人全部/本人/下属/关注场景均映射到生成的查询字段。`subordinateOwnerOnly=true` 由服务端从调用者可见部门子树和活动成员裁决，绝不由浏览器枚举成员；保存视图、临时高级条件、静态/动态排序和字段布局也均由服务端字段目录和范围策略验证。
- 查重残余：联系人已可按姓名或 E.164 电话在当前可见范围返回布尔结果；与客户相同，参考站的跨业务线查重方式仍需独立、受限的后端契约。

## 3. 租户访问与生产会话切换

- 用户场景：成员在 `/organization/tenants` 查看已授权租户；开发环境可从头部或该页选择已授权租户，切换后授权、导航和 Query 缓存隔离并刷新。
- 当前能力与缺口：`GET /organization/tenants` 现返回具名 `TenantAccessResponse[]`，`GET /organization/tenants/{targetTenantId}/access` 返回单个具名资格结果；两者均只校验资格，不切换会话或返回新认证上下文。Web 已提供服务端导航 `organization.tenants` 与租户访问页，并仅在显式开发身份下使用这两个端点更新当前标签页开发会话；全局租户建档、资料和停用不应借用该成员资格契约实现。
- 建议接口：认证服务提供 `POST /api/v1/session/tenant-switch`，请求只含已选择的 `targetTenantId` 与一次性 CSRF/认证上下文，响应返回新 server session 或受控重定向。成员目录应返回具名 tenant ID、展示名和当前项。
- 权限、错误、并发：服务端重新校验成员资格和会话；未授权返回具名错误码；切换使旧租户 session/缓存版本不可用。

## 4. 线索、联系人与产品导入（已实现）

- 已实现：`crm-import-drafts` 发布按对象类型的模板、私有上传意图、预览、确认、撤回和当前成员近七天历史；线索和联系人预览有任一行错误即关闭确认，产品按编码跳过已有及同文件重复项且不覆盖已有记录。错误报告只生成 `rowNumber,errCode` 的认证 Blob，源文件和错误资格固定保留七天；到期 worker 会标记草稿失效、撤回关系并进入既有精确回收流程。
- 权限与边界：入口同时需要对象写入和 `files:write`，服务端仍重新裁决字段策略、范围、重复规则、草稿上传者、文件检查及并发。浏览器不解析服务器错误信息、不保留源文件或报告内容，也不用单条创建循环模拟导入。

## 5. 市场活动

- 参考场景：市场活动默认页有名称检索、关联对象筛选、15 条/页、空态和创建入口；新建表单包含名称、关联对象、员工或部门参与人员、起止时间、类型、默认值为 0 的浏览数/提交数、预算、地址、简介和“每个用户一次”。它还提供两类最多九张的活动图片，以及由关联对象字段目录生成的公开表单字段勾选。2026-08-12 只读复核显示默认对象为客户、切换到线索后字段目录即时替换，当前租户还可出现租户配置对象；该次可见目录未含联系人。
- 已实现且已验证：后端新增版本化 `GET/POST /api/v1/marketing-activities`、详情、更新和软删除；`GET /api/v1/marketing-activities/configuration-options` 发布当前身份可用的关联对象目录、默认项与公开表单能力，当前目录为 `CUSTOMER|CONTACT|LEAD`。参与人员限制为当前租户的活动成员，时间范围与预算由领域和数据库共同校验；`marketing-activities:read/write/delete` 分别保护读、写、删，并在服务端复核成员和 version。隔离 MySQL 集成测试已覆盖真实 CRUD、查询、版本冲突、软删除及 OpenAPI schema；前端已从该运行实例刷新 snapshot 并生成类型。
- 当前前端范围：`/crm/marketing-activities` 在服务端导航与 read authority 下提供名称/关联对象/分页查询、详情、新建、编辑和删除；筛选、标签、默认值和表单入口均只消费该服务端目录。参与员工和部门分别只使用既有服务端在职成员与活动部门目录，写入成功会失效列表查询。浏览和提交计数需要在 `crm_marketing_activity` 以非负 `BIGINT`（默认 0）持久化，并在创建、版本化更新、查询和详情的具名 schema 中回显；领域、请求校验和数据库约束必须共同拒绝负数。`COVER` 与 `DETAIL` 图片已通过受控附件的上传意图、二进制传输、安全检查、认证 Blob 下载和版本化撤回闭环；活动还可版本化关联既有营销表单，并仅使用服务端回显的公开标识生成链接。
- 已实现的原子路径：线索活动可在同一请求嵌入一份尚未启用的线索采集表单；服务端在一个事务中复核活动、表单、字段目录与关系权限后创建并关联。既有表单 ID 与内嵌表单互斥，更新不接受内嵌表单；其余对象不会伪造通用字段目录。
- 仍需新契约：参考可见的租户扩展对象尚未有可存储的稳定 code，也没有其字段目录、表单可用性、对象化公开提交归属、原子结果或逐项错误码；服务端须在扩展目录和活动响应中一起发布这些事实，浏览器不能由显示名称、当前租户或 `CONTACT` 等既有 code 推导。批量活动动作同样需要独立版本化接口。

## 6. 合同、回款、发票、回访的全局工作台

- 已实现：`POST /api/v1/contracts/query`、`/receivables/query`、`/invoices/query`、`/return-visits/query` 均是服务端范围化分页查询，已支持关键词、下属/本人场景、状态、保存/临时高级条件、静态及字段目录确认的动态排序和列布局。Web 不拼接客户上下文查询，也不在浏览器排序或过滤已加载记录。
- 仍需新契约：参考站若要求批量状态动作，须为每种业务对象发布独立的版本化请求、可执行动作投影、逐项或原子结果及具名冲突码。

## 7. 仪表盘目标与完整销售简报

- 已实现：`DashboardOverviewResponse` 已按同一范围/时间快照发布 KPI、趋势、排行榜与合同目标的 `AVAILABLE|EMPTY|UNAVAILABLE` 投影。成员月度和部门年/季/月合同目标有独立读写、版本化批量设置及原子 CSV 导入接口；浏览器只刷新服务端真实查询，不推导组织实际、完成率或趋势。
- 仍需新契约：多看板、自定义指标或参考站新增图表模块应由服务端发布具名看板定义、范围/时间/权限投影、模块状态和稳定版本；不可见模块不能以零值回退，浏览器也不能从既有合同或回款数据拼装。

## 8. 商机联系人与客户一致性（已实现）

- 已实现：`POST /api/v1/opportunities`、完整 `PUT /api/v1/opportunities/{id}`、联系人替换及首要联系人更新都在调用者可见性检查后验证每个联系人属于目标客户；不可见联系人统一返回资源未找到，可见但跨客户或未关联客户的联系人返回审阅后的参数错误。首要联系人仍由领域层限制在去重后的关联集合中。
- 关系完整性：迁移 `V96__enforce_opportunity_contact_customer.sql` 为关系表持久化 `customer_id`，并以 `(tenant_id, opportunity_id, customer_id)`、`(tenant_id, contact_id, customer_id)` 复合外键约束商机、联系人与客户三者。因而绕过 HTTP 或并发改联系人/商机客户也不能落下跨客户关联。
- 验证：`OpportunityIntegrationTest` 新增了跨客户创建、联系人替换、首要联系人、完整客户替换及直接关系旁路写入的覆盖。此行为未改变 OpenAPI schema，无需刷新前端生成类型；仍应在具备 Docker 的隔离 MySQL 环境运行该集成套件和商机创建 E2E 回归。

## 9. 产品图片分组与创建阶段媒体（已实现）

- 已实现：`V97__add_product_image_drafts.sql` 为产品关系增加闭合 `PRIMARY|DETAIL` 图片组，并存储 tenant/uploader 绑定、版本化、一次性私有草稿及精确候选集合。产品受控附件列表和上传意图接受 `productImageType`；仅产品、PNG/JPEG、每组最多 9 个上传中或已发布关系，稳定顺序由服务端 available time/file ID 决定。
- 创建闭环：`POST /api/v1/product-image-drafts` 创建私有草稿；各组的 upload intent、二进制内容上传、状态查询和版本化撤销使用专用路由。`ProductCreateRequest.productImageDraftId + productImages` 只接受该 uploader 的完整 CLEAN 精确集合，并在产品创建事务中发布、绑定和消费草稿；缺少、冗余、重复、过期、被拒绝或版本冲突都失败关闭并沿用受控清理。
- 前端已接入：快照和生成类型已从同一已迁移实例刷新。新建页只在 `files:write` 下创建私有草稿、按组上传并展示检查状态；仅所有已选择文件为 `UPLOADED` 时才把精确 ID 随产品创建提交，取消或清空会显式撤回草稿。详情按 `PRIMARY|DETAIL` 分组查询，并分别支持受控上传、下载和版本化撤回；浏览器不从 MIME、名称、顺序或缓存推导类别、上限、检查状态或绑定资格。

## 10. 保存筛选方案的外露条件（已实现）

- 参考场景：核心 CRM 列表的“展开筛选”是保存场景的视图状态。高级筛选的每个条件可显式标记“外露”；展开后仅展示这些服务端保存的条件，并提供应用与清空外露值的动作。
- 已实现契约：保存视图创建、更新和读取统一使用独立的 `SavedViewConditionRequest/Response { fieldCode, operator, values, exposed }`；`POST /query` 仍只接收不含 UI 元数据的 `FilterConditionRequest[]` 或 `savedViewId`。持久化兼容既有条件 JSON，缺失 `exposed` 时收敛为 `false`，且保存、字段/范围校验和版本冲突保持同一原子边界。
- Web 闭环：方案编辑器和“高级筛选 → 保存为筛选方案”均让 `saved-views:write` 成员逐条件选择“在列表中外露此条件”；直达流程还可在创建后以响应的 `id/version` 设置默认方案。选择含外露条件的视图后，`saved-views:read` 成员可展开已发布条件、只修改其值后应用；未外露条件继续保留在同一临时查询中。清除或收起会清掉临时条件并恢复服务端的原始 `savedViewId`，不会改写保存方案、URL 或浏览器存储。
- 回归：后端 MySQL 集成测试断言 JSON 往返、历史兼容和 OpenAPI 组件引用；Web 刷新快照后覆盖生成契约、外露控件、展开/应用/清除流程和 `savedViewId` 与临时 `conditions` 的互斥。
