# 前端架构基线

## 边界

本应用是 `atom-crm` 的独立 SPA。浏览器只请求相对路径 `/api`，开发环境由 Vite 代理到后端；生产环境由同源网关代理。前端不计算 tenant、actor、authority、role 或 data scope，也不以本地权限判断代替服务端授权。

服务端状态只由 TanStack Query 缓存；路由、分页、排序、搜索和筛选进入 URL；未提交表单归 React Hook Form；短生命周期跨组件 UI 状态才可使用 Context 或 Zustand。业务实体不得复制到本地全局状态。

## 契约流程

`/v3/api-docs` → `openapi/atom-crm.json` → `src/api/generated/schema.d.ts`。CI 会重新生成类型并检查 Git 漂移。快照只能反映拉取时的后端；每次联调和后端 API 变更都必须刷新它。

所有 API 错误会归一为 `ApiError`（P1 实现）。界面根据稳定的 `errCode` 取中文词条，绝不直接把服务端英文 `errMsg`、堆栈或原始请求显示给用户。HTTP 409 必须区分 `VERSION_CONFLICT`、`CONCURRENT_OPERATION` 和 `RESOURCE_ALREADY_EXISTS`。

## P1 应用 bootstrap

`AuthProvider` 先创建环境对应的 `AuthAdapter`，再由 `BootstrapProvider` 以 `(tenant, actor)` 身份键请求 `/api/v1/authorization/me` 与 `/api/v1/navigation`。这两个结果只保存在 TanStack Query；身份键变化会移除 bootstrap 查询，避免跨租户或跨成员复用缓存。`ResponsiveAppLayout` 仅消费后端导航树，客户端 authority 判断只用于隐藏不可达入口和路由提示，不能替代服务端授权。

应用壳以单一主题令牌统一页面底色、表面、边框、文字、反馈色、控件高度和圆角（令牌定义在 `src/app/providers/theme.ts`，认证壳与公共页共用同一份）。桌面为 56px 白色顶部模块导航，CRM 上下文另有 240px 侧栏；小于移动断点改为带安全区的抽屉。呈现形态不会改变导航来源或授权。应用头部不再重复页面的一级标题，快捷入口仍逐项由 bootstrap authority 守卫；主内容提供键盘跳过链接、可见焦点和带文字提示的图标操作。跳过链接的落点是 `tabindex=-1` 的壳层内容容器而非第二个 `main`，由受保护路由页面提供唯一主地标，因此浏览器和辅助技术不会遇到嵌套主地标。

工作台读取 `/api/v1/dashboard/overview` 的服务端卡片。金额只做展示格式化，不在浏览器中进行 JavaScript 金额运算；`UNAVAILABLE` 卡片只显示降级状态。普通读取查询只会对 5xx 最多自动重试一次；bootstrap 失败立即显示统一状态页并由用户显式重试。mutation 永不自动重试，HTTP 409 由统一状态页提示刷新。

## P2 Mutation 冲突处理

`MutationConflictNotice` 仅把 `ApiError(409)` 的稳定 `errCode` 分为 `VERSION_CONFLICT`、`CONCURRENT_OPERATION` 与 `RESOURCE_ALREADY_EXISTS`。前两个只在用户明确选择“保留当前输入并刷新”或“放弃输入并刷新”后把意图交给页面处理；组件不自行刷新、重试或清空表单。重复资源只提供确认，不进入刷新冲突流程；未知 409 也不会被误判为可安全刷新的版本冲突。

## P2 受保护下载

附件与 CRM FILE 字段内容只通过 API client 的已认证 fetch 获取 Blob；成功后才允许以短生命周期的 `blob:` URL 触发浏览器保存。客户端不会渲染或暴露受保护资源的裸 URL，文件名仅从服务端 `Content-Disposition` 解码后使用，并会移除路径和控制字符。当前不支持媒体预览、iframe 或 Range 播放，等待生产认证的 Cookie/CSRF 或签名 URL 方案定案。

## P2 列表基础

`createEntityQueryKeys` 强制把身份键带入每个实体的列表和详情 Query Key。通用分页适配器将后端一基页码和 `Pager.totalNum = -1` 的“无总数”契约转换为 UI 状态；无总数时不伪造总页数，只显示上/下一页操作。`PageHeader`、`FilterBar` 与 `DataWorkspace` 统一标题、页面动作、URL 可恢复筛选、已生效条件和错误容器；`ResponsiveDataList` 在桌面使用 sticky 表头、横向滚动和可选固定列/批量操作槽位，在移动端继续使用业务摘要卡片。客户列表是首个消费者，搜索与分页参数仍保留在 URL。

客户查询与基础读写现在由具名 `CustomerPageResponse` 和 `CustomerResponse` 发布；前端使用生成类型发起请求，仍在显示边界做窄、失败关闭投影，不维护完整手写 DTO。字段元数据等独立契约继续按各自生成 schema 接入，不能用客户响应推断字段访问。

## P3 客户详情读取

客户列表名称可进入 `/crm/customers/:customerId`，详情以 identity-aware Query Key 请求服务端的可见记录。当前详情只投影基础客户字段，明确排除 `customFields` 与 `fileFields`；二者的展示还依赖有效字段访问上下文和受控文件通道。`DetailWorkspace` 将服务端业务概览作为宽屏独立摘要栏、窄屏内容前置摘要，原有查询、权限动作和弹窗不改变。无效 ID、404 与其他读取错误分别进入受控状态页，页面不从 URL 或本地状态推导数据范围。

## P3 客户新建

`/crm/customers/new` 只在服务端返回 `customers:write` 时显示入口并允许进入。基础表单使用生成的 `CustomerCreateRequest`，空的可选输入不会伪装成字段更新；创建成功后仅失效客户列表并填充新记录详情缓存。`FormWorkspace` 为字段和保存操作提供两列/移动单列布局及安全区 sticky footer，但不保存草稿或字段偏好。负责人、上级客户、地址、标签、动态字段和 FILE 草稿均各自通过受权限约束的选择器或状态机进入表单；协作者继续是详情中的独立完整替换流程。

## P3 客户基础编辑

`/crm/customers/:customerId/edit` 只发送相对加载基线发生变化的基础字段，并保留原始 version。版本冲突或并发操作时，选择保留草稿只会重新读取服务端版本并锁定再次提交；用户必须显式放弃草稿才会载入新基线。该流程不会自行重试、清空或用新 version 覆盖旧草稿。编辑页与创建页共用 `PageHeader` 和 `FormWorkspace`，不影响基线、草稿锁定或字段级 WRITE 权限的服务端裁决。

## P3 客户个人关注

详情页的“关注/取消关注”只调用当前成员的 `/star` 动作；它只要求该客户对当前成员可读，不混入客户版本或业务字段权限。服务端成功后才更新详情缓存，并失效客户列表缓存，失败不改变页面中的已关注状态。

## P3 客户业务概览

客户详情读取固定的七项业务概览。服务端对每项关联域分别检查数据范围、authority 和字段可见性；前端只按响应中的 `AVAILABLE` 或 `UNAVAILABLE` 显示，绝不基于当前客户权限推断联系人、商机、合同、发票、回款或回访的可见性。金额仅格式化服务端值，不在浏览器计算。

## P3 客户跟进时间线读取

客户详情仅在 `activities:read` 下以身份隔离 Query Key 查询 `POST /api/v1/activities/query` 的固定首页；`ActivityPageResponse` 发布服务端对当前成员和客户裁决的一页 `ActivityResponse`，请求只包含当前详情客户 ID、固定 `CUSTOMER` subject type 和 `page=1,size=20`。进入浏览器的窄投影仅为活动 ID、方式、目的、内容、发生时间和下次联系时间，关联对象、作者、version、附件和动态字段均被丢弃。服务端继续复核活动权限和客户可见性；前端不从详情、关系、类型或缓存推断活动范围，查询失败只局部提示。

## P3 客户跟进基础新建

客户详情只有同时具备 `activities:read` 与 `activities:write` 时才显示“写跟进”。方式目录完全来自受读取权限保护的 `GET /api/v1/activities/options`，浏览器不补默认方式或手输 code；提交只带当前详情客户 ID、固定 `CUSTOMER` 类型、选中的服务端方式、可选目的、内容和用户确认的发生时间。成功后仅失效同一身份和客户的时间线查询；关联对象、附件、下次联系和模板字段保持在独立的权限边界。

## P3 客户跟进编辑与删除

时间线只对服务端投影为 `FOLLOW_UP` 的条目显示编辑、删除入口，且都要求 `activities:read` 与 `activities:write`。点击后先读取活动详情的完整基线；编辑只提交用户明确修改的方式、目的、内容和发生时间，并保留详情返回的 version、关系集合和下次联系时间。若关系基线不完整，运行时解码器失败关闭，前端不会冒险执行会替换关系的更新；删除只带当前详情 version。服务端仍复核调用者归属、目标客户范围、字段访问、活动状态和并发，409 必须经用户明确刷新，不自动重试。

## P3 客户上下文回访列表

客户详情只在 `return-visits:read` 下开放 `/crm/customers/:customerId/return-visits`，该路由不是导航树菜单项。列表以身份隔离 Query Key 发送生成的 `ReturnVisitQueryRequest`，路径客户 ID、页码、每页数量和关键词均为普通查询输入，不能代表授权；后端继续复核回访 authority、`CUSTOMER` 字段未遮罩访问和客户可见性。列表编号进入同一客户上下文的详情路由，并以独立身份隔离 Query Key 请求 `GET /api/v1/return-visits/{returnVisitId}`；详情必须要求响应中的未遮罩客户 ID 与路径一致。新建路由在 `return-visits:write` 下只提交路径客户、用户确认的回访时间和可选备注，负责人保持服务端当前成员默认；成功响应必须回显同一客户 ID 才会写入详情缓存或跳转。编辑路由额外要求同一读写 authority，始终先读取服务端详情，以返回的 `version`、回访时间和未遮罩备注为完整基线；任一基线字段缺失即失败关闭，避免遮罩值被误写为空。B15 后端契约明确：更新请求省略 `contactId` 与 `contractId` 时会保留服务端当前关联；编辑表单因此从不提交关联、动态字段或附件。详情中的联系人与合同选择复用该完整基线，分别还要求 `contacts:read + customers:read` 或 `contracts:read + customers:read`；候选按当前客户从服务端查询，运行时只接受回显该客户 ID、稳定 ID 和未遮罩名称的项目，且仅在 B15 响应明确给出相应关系为 `VISIBLE` 或 `EMPTY` 时开放。选择/更换请求只携带一个正 ID、基础基线与原始 version，另一个关系省略以保留；服务端仍重新裁决候选可见性、归属、字段写权限和并发。详情中的负责人变更额外要求 `return-visits:assign` 与 `organization:read`，候选只来自服务端可见的在职成员目录，提交当前 version；可分配范围和 `OWNER_ACTOR` 字段权限仍由服务端重新裁决。OpenAPI 现以 `ReturnVisitPageResponse` / `ReturnVisitResponse` 发布分页和基础读写成功响应；前端用生成类型接收后仍只解码回访 ID、version 和该客户关系，其余字段允许为服务端字段策略产生的 `null`，不读取动态字段、附件或关联详情，也不以隐藏字段补全页面。

回访关系清除已依据刷新后的 `ReturnVisitUpdateRequest.contactId`、`contractId: number | null` 契约交付：B15 区分省略（保留）和显式 `null`（清除），页面只在用户确认后以当前详情的完整基础字段和 version 发送其中一个 `null`，从不使用类型断言或未类型化请求，也不会同时改写另一个关系。

## P4 客户上下文合同列表

客户详情仅在同时具有 `contracts:read` 和 `customers:read` 时开放 `/crm/customers/:customerId/contracts`，该路由不是导航树菜单项。列表以身份隔离 Query Key 发送生成的 `ContractQueryRequest`，路径客户 ID、页码、每页数量和关键词都只是查询输入，不能代表授权；后端继续复核合同 authority、`CUSTOMER` 字段未遮罩访问和客户可见性。`ContractPageResponse` 以具名合同项发布当前页，运行时窄投影仍只接受 ID、非负 version 和回显的正 customer ID，再保留名称、编号、日期、联系人/负责人引用与状态；与路径客户不一致或缺少稳定身份的行会丢弃。金额、折扣、产品、动态字段、文件字段和协作者不会进入缓存或页面，也不执行金额格式化或算术，等待 BigDecimal JSON 契约定案。

合同编号进入 `/crm/customers/:customerId/contracts/:contractId`。详情同样以身份隔离 Query Key 请求 `GET /api/v1/contracts/{contractId}`，只有返回的正 customer ID 与路径客户完全相等才渲染；否则受控地失败关闭。详情只保留合同的基础文本/日期/引用/status 与服务端可见的产品名称、编码、分类、单位和数量。产品区域额外以 `products:read` 做 UI 守卫；该守卫不扩大读取范围，快照为空或缺失时保持空态。任何金额、价格、折扣、行金额、总额、协作者、动态字段和附件都会在运行时投影中丢弃。

新建路由 `/crm/customers/:customerId/contracts/new` 需要 `contracts:write` 与 `customers:read`。表单适配生成的 `ContractCreateRequest`，发出路径中的正客户 ID、用户确认的名称和编号，以及可选的产品 ID/数量；产品候选只通过 `products:read` 下的服务端目录读取，浏览器不允许手输产品 ID，且没有目录权限时只可创建空产品集合。价格、折扣和金额不进入候选、选择状态、请求或浏览器计算。浏览器不猜测或复制负责人、联系人、商机、日期、协作者、动态字段或附件。成功响应必须通过同一窄合同解码器，并且只有回显 customer ID 与路径相符且成员具备 `contracts:read` 时才写入身份隔离详情缓存并跳转；否则仅显示服务端返回的 ID。服务端继续裁决客户可见性、字段策略、规范化编号唯一性、产品集合和写入权限。

合同编辑保持关闭。当前 `PUT /api/v1/contracts/{contractId}` 会整体替换客户、关联、日期、产品、折扣与动态字段；详情快照既没有成功响应 schema，也没有字段可见状态，因而 `null` 不能安全当作真实空基线。产品 `unitPrice` 省略又会被服务端替换为当前目录价，浏览器不能在不处理历史成交金额的前提下重放产品行。需要后端提供完整可写基线（含已定 BigDecimal JSON 表达）或显式 PATCH/保留语义，并刷新 OpenAPI 后才可实施。

## P4 客户上下文开票资料列表

客户详情仅在同时具有 `invoices:read` 和 `customers:read` 时开放 `/crm/customers/:customerId/invoice-profiles`，该路由不是导航树菜单项。列表以身份隔离 Query Key 发送生成的 `customerId` 查询参数；路径 ID 不能代表授权，后端继续复核发票读取权限和客户可见性。由于快照将成功响应标为泛型对象，运行时只接受数组中的正资料/客户 ID、非负 version、非空抬头类型和抬头，并逐条要求 customer ID 与路径相等。投影只保留抬头类型、抬头、税号与更新时间；银行名称、账户、注册地址、电话和备注在解码边界丢弃，不进入缓存、页面或日志。

新建路由 `/crm/customers/:customerId/invoice-profiles/new` 需要 `invoices:write` 与 `customers:read`。首期的表单适配生成的 `InvoiceProfileRequest`，却只允许发出路径客户 ID、用户确认的抬头和常量 `INDIVIDUAL`；不会输入、重放或推断组织抬头的税号、银行、地址、电话或备注。成功响应仍通过窄投影；只有回显 customer ID 与路径相等并拥有资料读取权限时才失效列表并跳转，否则只显示成功 ID。组织抬头与全量编辑需要敏感字段的可读/遮罩状态和完整可写基线，当前保持关闭。

列表中每条资料只在 `invoices:delete` 下展示删除操作。用户确认后，浏览器只将该窄投影返回的资料 ID 和 version 发送到 `DELETE /api/v1/invoice-profiles/{profileId}`；不以资料内容、当前成员或缓存推导 owner scope。成功只失效同一身份的资料列表，服务端重新裁决可见客户、删除权限和版本冲突。组织抬头与全量编辑仍保持关闭。

## P4 客户上下文发票列表

客户详情仅在同时具有 `invoices:read` 与 `customers:read` 时开放 `/crm/customers/:customerId/invoices`，该路由不是导航树菜单项。列表以身份隔离 Query Key 发送生成的 `InvoiceQueryRequest`，路径客户 ID、页码和每页大小不能代表授权；后端继续复核发票 authority、`CUSTOMER` 字段未遮罩访问和客户可见性。`InvoicePageResponse` 以具名发票项发布当前页，运行时窄投影只接受正发票/客户 ID、非负 version 与可选合同 ID，再保留申请/发票编号、类型、状态和日期；不匹配路径客户的行失败关闭。金额、开票抬头、税号、银行、联系人、收件信息、物流、备注、动态字段和附件不进入缓存、页面或日志。

同一读取权限下，申请编号在桌面表格和移动卡片中都可进入 `/crm/customers/:customerId/invoices/:invoiceId`。详情只请求该发票并复用列表窄投影，返回 customer ID 缺失或不等于路径客户即失败关闭；详情没有任何写操作。创建、编辑、开具、重置、负责人和删除仍等待各自的可写/敏感字段边界。

## P4 客户上下文回款列表

客户详情仅在同时具有 `receivables:read` 与 `customers:read` 时开放 `/crm/customers/:customerId/receivables`，该路由不是导航树菜单项。列表以身份隔离 Query Key 发送生成的 `ReceivableQueryRequest`，路径客户 ID、页码和每页大小不能代表授权；后端继续复核回款 authority、`CUSTOMER` 字段未遮罩访问和客户可见性。`ReceivablePageResponse` 以具名回款项发布当前页，运行时窄投影只接受正回款/客户 ID、非负 version 与可选合同/回款计划 ID，再保留回款编号、日期和状态；不匹配路径客户的行失败关闭。金额、支付方式、备注、负责人、动态字段和附件不进入缓存、页面或日志。

同一读取权限下，回款编号在桌面表格和移动卡片中都可进入 `/crm/customers/:customerId/receivables/:receivableId`。详情只请求该回款并复用列表窄投影，返回 customer ID 缺失或不等于路径客户即失败关闭；服务端未遮罩回显回款日期且成员同时具备 `receivables:write` 与 `contracts:read` 时，页面可 PATCH 这一项及 version。关联计划、金额、支付方式、备注、负责人、动态字段和附件仍没有浏览器编辑基线；创建、负责人和删除保留各自的可写/敏感字段边界。

## P4 客户上下文回款计划列表

`/crm/receivable-plans` 是现有回款页面内的局部全局工作区，不是服务端导航树条目。它以身份隔离查询键发送生成的 `ReceivablePlanQueryRequest`，只保留服务器回显的稳定计划/客户/合同引用、期数、到期日、服务端金额和状态；分页汇总由独立 `POST /api/v1/receivable-plans/summary` 在同一筛选与服务端数据范围下返回。全局行的“新建回款”只在现有回款写入和关联目录读取权限均存在、且该行客户/合同关系非空时构造固定客户上下文路由。页面不信任该行或 URL 的计划 ID：回款表单重新读取计划、合同和可用计划目录，严格匹配客户/合同/计划后才预选；创建后失效回款及计划列表缓存，并经固定 `returnTarget` 回到原计划工作区。未知目标、不可见关系或验证失败均不会预选或改变提交数据。

客户详情仅在同时具有 `receivable-plans:read` 与 `customers:read` 时开放 `/crm/customers/:customerId/receivable-plans`，该路由不是导航树菜单项。列表以身份隔离 Query Key 发送生成的 `ReceivablePlanQueryRequest`，路径客户 ID、页码和每页大小不能代表授权；后端继续复核回款计划 authority、`CUSTOMER` 字段未遮罩访问和客户可见性。`ReceivablePlanPageResponse` 以具名计划项发布当前页，运行时窄投影只接受正计划/客户 ID、非负 version 与可选合同 ID，再保留期数、到期日期、进度和状态；不匹配路径客户的行失败关闭。计划、已收和剩余金额、支付方式、备注、负责人、动态字段和附件不进入缓存、页面或日志。

同一读取权限下，期数在桌面表格和移动卡片中都可进入 `/crm/customers/:customerId/receivable-plans/:planId`。详情只请求该计划并复用列表窄投影，返回 customer ID 缺失或不等于路径客户即失败关闭；详情没有任何写操作。创建、批量创建、编辑和删除仍等待各自的可写/敏感字段边界。

## P5 Work 任务基础浏览

`/work/tasks` 与 `/work/tasks/:taskId` 都以 `work-tasks:read` 作为路由和请求的 UI 防护，且不是导航树菜单项。列表以身份隔离 Query Key 发送生成的 `WorkTaskQueryRequest`；URL 分页、任务 ID 和当前身份都不构成参与者可见性证明，服务端继续裁决。`/work/tasks/new` 还要求 `work-tasks:write` 与 `organization:read`，成员目录查询同样以身份和检索关键字隔离，并只解码服务端在职可见的 `{ actorId, displayName }` 选项。创建请求只包含修剪标题、选中的 actor ID 和可选到期时间；优先级坚持使用服务端默认，描述、关注人、关联、附件、提醒和周期配置不保留。`/work/tasks/:taskId/edit` 进一步要求 `work-tasks:write` 与 `work-tasks:manage`，并以独立身份隔离键读取同一资源的管理编辑基线。该基线只保留 ID、version、开放状态、标题、描述、优先级和到期时间；完整 PUT 只重放这些结构字段和 version，成功响应重新收敛为窄浏览投影。详情的重新分配另需 `organization:read`，仅在开放状态使用同一身份隔离的成员目录查询；请求只有候选 actor ID 和窄投影 version，成功后仍收敛为窄投影并失效列表和评论。关注人替换也使用独立身份隔离的完整基线，但只保留 ID、version、开放状态和完整唯一的关注人 actor ID 列表；候选同样来自成员目录，浏览器最多提交 50 个去重 actor ID 与该基线 version，成功后只写回窄投影并失效列表和评论。服务端对创建人也允许结构管理，但前端不会用本地身份和原始创建人 ID 推导资格，需后端增加 caller capability 后才能放开创建人入口。OpenAPI 快照把成功响应标为泛型对象，运行时窄投影要求正任务 ID、非负 version、非空标题和布尔 `overdue`，再保留可选优先级、到期时间和状态。任务描述、创建/负责人、关注人、业务关联、重复任务来源、提醒、工作台投影版本和生命周期时间不会进入浏览缓存、详情页面或日志；详情响应 ID 必须精确匹配路径，否则失败关闭。拥有 `work-tasks:write` 且详情状态明确为 `TODO` 或 `IN_PROGRESS` 时，页面可调用开始、退回待办或完成动作，只发送当前 version；服务端仍复核当前处理人、状态机和并发。详情还以独立身份隔离缓存读取评论的固定首页；窄评论投影要求评论/任务 ID、version 与非空内容，并只保留内容和创建时间，评论人及更新时间被丢弃。具有写入权限的参与者可提交纯文本评论，服务端继续裁决可见性；由于作者身份不进入前端，删除评论保持关闭。管理者可取消/删除符合服务端状态前提的任务；提醒从独立的版本化计划基线读取并完整替换，均不以浏览器身份推导创建者资格。

业务关联清除不需要读取完整基线：服务端明确定义在类型与 ID 同时省略时清除关系，并避免解析旧目标以免泄露已被遮罩或删除的对象。故开放任务详情可在用户确认后仅发送窄投影 version，成功响应仍收敛为窄投影；选择和替换仍需后端提供涵盖客户、联系人、线索、商机、合同、发票、回款和回款计划的统一可写候选目录，当前浏览器不会从局部列表、路径或授权字符串推导这些候选。

取消同样不需完整基线，但服务器同时授予创建人和管理者。由于任务窄投影不含经审查的 caller capability，前端只向 `work-tasks:manage` 成员展示开放任务的二次确认入口，发送当前 version 后将成功响应重新收敛为窄投影；创建人专用入口等待后端补充能力。

删除只在 `TODO` 窄投影下向管理者显示，但“从未开始、无评论、无附件历史”不是浏览器可判定的删除前提。确认后浏览器只以查询参数发送 version；服务端核验完整前提后，浏览器移除当前详情和评论查询并返回列表。创建人专用入口同样等待 caller capability。

任务附件是详情内的独立只读弹层，额外受 `files:read` 守卫。弹层只在显式打开后以身份、任务 ID 和分页参数隔离查询缓存；每条泛型返回值仅保留 file ID、version、名称和可选媒体类型，其他附件元数据丢弃。下载从认证客户端取得 Blob 后临时保存，绝不把受保护内容 URL 交给裸链接或媒体元素。上传、撤回、预览和附件详情不纳入此切片：它们需要覆盖意图、原始内容、异步检查/发布、失败回收与并发版本的独立状态机；当前 OpenAPI 对原始二进制内容请求也缺少可用类型。

`/work/task-series` 是独立的周期任务列表，使用 `work-tasks:read` 与身份隔离 query key 获取服务端分页。运行时投影只接受正系列 ID、非负 version、非空标题、`DRAFT`/`ACTIVE`/`PAUSED`/`ENDED` 状态和满足服务端约束的完整日历规则；成员、描述、自动化游标、未来实例计数、失败原因及时间戳不进入缓存。任一可读成员可按用户动作打开独立身份隔离的实例分页；每条只在返回 series ID 匹配目标、正发生序号、合法实际到期时间和 `MATERIALIZED`/`SKIPPED` 状态完整时保留三项事实，实例/生成任务 ID、批次、名义时间、时区、偏移、原因和记录时间全部丢弃。`/work/task-series/new` 还要求 `work-tasks:write` 与 `organization:read`，处理人只能从身份隔离的服务端在职成员目录选择；创建草稿请求只含修剪标题、处理人、频率/间隔、星期或月日、IANA 时区、起止日期和本地时间，描述、优先级、关注人、自动化状态和提醒模板不发送。成功响应仍先经规则窄投影解码，只失效当前身份的列表。拥有 `work-tasks:write + work-tasks:manage` 的管理者可在明确确认后停止未来发生，浏览器只发送窄投影 ID 与 version，成功后仅失效列表；服务端保留已生成任务和发生历史，并复核可见性、资格与并发。同一管理者可按用户动作打开独立身份隔离的未来提醒模板基线，只保留 series ID、version 和最多 8 条固定步骤；保存完整替换只发送步骤和该基线 version，不使用列表 version，也不读取成员、实例、自动化或通知状态。系列的更新与启停服务端也授权“创建者或管理者”，但只读投影没有 caller capability，浏览器不会从本地身份或原始创建人 ID 推导资格；这些动作仍等待各自的经审查基线。

## P3 客户创建前查重

新建客户表单提供显式“检查重复”操作，只提交已经过本地格式校验的名称和联系电话。服务端只返回当前成员可见范围内的布尔结果，前端不展示或缓存任何匹配客户信息；检查结果仅说明最近一次输入，且不会替代创建时服务端的最终校验。

## P3 客户负责人修改

负责人选择器只查询服务端可见且在职的成员，并以身份键隔离查询缓存。入口同时受 `customers:assign` 与 `organization:read` 守卫，提交时带详情加载时的 version；后端仍独立裁决负责人字段 WRITE 权限、客户 owner scope 和可分配成员范围。

## P3 客户协作者管理

协作者管理仅在 `customers:assign` 下按需读取独立、服务端授权的 `CustomerCollaboratorBaselineResponse`。该完整基线同时携带非负 `version`、成员列表和服务端验证的调用者状态；解码器遇到未知状态/access、无效成员或重复成员会失败关闭，绝不丢弃条目后提交全量替换。基线加载、错误或缺失时所有草稿操作和保存均关闭；保存只使用基线 version。新增成员还要求 `organization:read`，且默认只读。`customers:write` 下的自助退出只提交当前详情 version，成功后清除同一身份的详情/协作者缓存并返回列表；服务端仍裁决 owner scope、成员在职状态、成员可分配性和乐观锁版本。

## P3 客户层级

详情页读取服务端返回的可见祖先与后代，并仅对这些已返回节点做关系展示和候选排除；它不在浏览器推断隐藏节点。设置上级时使用服务端可见的客户查询结果和当前 version，清除上级使用同一生成请求契约的仅 version 载荷。循环、层级容量、字段 WRITE 权限与 data scope 都由服务端最终裁决，任何 409 不会被自动重试。

## P3 客户状态

锁定与成交状态必须作为同一 versioned 请求整体提交。客户端仅在两个值均由服务端明确返回且成交状态属于当前受支持枚举时开放编辑，避免以遮罩或缺失值覆盖服务端状态。

## P3 客户标签

详情页的标签管理同时以 `customers:write` 和 `GET /api/v1/customers/tags` 的成功结果为前置条件：后者由服务端确认当前成员能读取未遮罩的标签字段，前端才会用详情原始 tags 作为完整替换草稿。草稿最多 50 个、单项最多 50 个字符，空值或规范化重复值会在浏览器阻止提交；保存只带用户确认的完整 tags 与详情原始 version。成功响应覆盖当前身份详情缓存并失效列表与标签目录；字段级权限、数据范围与冲突继续由服务端裁决，409 不自动重试。

## P3 客户删除

详情页仅在服务端明确授予 `customers:delete` 时显示删除确认，并只提交当前详情的 version。成功后移除客户域缓存并返回列表；前端不根据可见层级判断是否仍有活动下级客户，也不尝试撤回附件或 FILE 字段绑定。服务端独立裁决 owner scope、软删除依赖和并发；409 必须由用户显式选择刷新，不自动重试。

## P3 客户 CSV 导出

首期只请求稳定的 `customer_name` 列和当前关键词，避免把 `GET /fields/**` 的 `fields:read` 门槛错误附加到只拥有 `customers:export` 的成员。服务端重新裁决导出权限、数据范围和未遮罩字段访问，并负责生成带公式注入防护的 CSV；客户端不拼装 CSV 内容，只以受控 Blob 下载响应。若要支持可配置列，后端必须新增按 `customers:export` 与有效字段访问共同裁剪的导出字段元数据接口，前端不能复用管理字段的 `/fields/**` 接口。

## P3 附近客户

`/crm/customers/nearby` 在 `customers:read` 守卫下，只有用户主动触发浏览器定位后才请求 `GET /api/v1/customers/nearby`。经纬度只保存在页面短生命周期状态和对应的身份隔离 Query Key，不进入 URL、持久化存储、日志或页面展示；半径、页码和每页数量保留在 URL。首期不接入地图或第三方地图 Key，只按服务端返回的距离排序分页；运行时投影仅保留嵌套客户的既有窄列表字段与非负距离，不能从地址、坐标或缓存推断额外位置数据。服务端仍负责 `ADDRESSES` 未遮罩访问、数据范围与最终查询授权。

## P3 联系人列表

`/crm/contacts` 以联系人身份键、页码和关键词查询服务端可见联系人。`ContactPageResponse` 明确发布受服务端范围和字段策略裁决的一页 `ContactResponse`；运行时仍只投影名称、职务、联系方式、已获许可的客户与负责人引用、状态、关注和标签，不以联系人权限或具名响应推断任何客户详情、隐藏字段或数据范围。详情与新建入口分别受各自路由和 authority 边界保护；关联客户编辑在其选择器与可见性边界交付前不由列表伪造入口。

## P3 线索列表

`/crm/leads` 以线索身份键、页码和关键词查询服务端可见线索。`LeadPageResponse` 明确发布受服务端范围和字段策略裁决的一页 `LeadResponse`；运行时仍使用窄投影保留名称、职务、联系方式、已获许可的客户与负责人引用、状态、关注和标签。动态字段、附件、地址、协作者与未获许可的关联对象都不进入浏览器展示。页码和关键词保留在 URL，路由与请求均要求 `leads:read`；转换在具备独立契约与权限边界后单独交付。

## P3 线索详情读取

`/crm/leads/:leadId` 在 `leads:read` 守卫下，以身份隔离的 Query Key 读取服务端可见线索。运行时窄投影只保留基础字段、已获许可的客户/负责人/层级/转换联系人 ID、状态、关注和标签，明确排除 `customFields`、`fileFields`、地址与协作者；无效 ID、404 和其他读取失败均进入受控状态页。返回的引用仅作展示，不触发或推断其他对象读取。

## P3 线索基础新建

`/crm/leads/new` 仅在 `leads:write` 下可进入；使用生成的 `LeadCreateRequest` 提交名称、职务、联系方式、网站、说明和下次联系时间等基础字段。新建成功后，仅以服务端返回的投影填充当前身份的详情缓存并失效线索列表。负责人、客户、上级、标签、协作者、地址、动态字段和 FILE 草稿都必须在具备独立的可见性约束选择器或流程后再加入创建请求。

## P3 线索基础编辑

`/crm/leads/:leadId/edit` 仅在 `leads:write` 可用且服务端未标记线索为已转换时显示入口。更新请求只带相对详情基线发生变化的名称、职务、联系方式、邮箱、网站、说明和下次联系时间，并携带加载时的 version。下次联系时间从详情转换为本地日期时间控件值，只有用户修改才发送；清空时以生成契约的 `null` 明确表达，未修改则保持省略。版本冲突或并发操作必须由用户显式选择刷新路径，绝不自动重试。地址、动态字段和 FILE 字段仍保留为独立受可见性约束流程。

## P3 线索层级

详情页读取 `GET /api/v1/leads/{leadId}/hierarchy` 所返回的受数据范围裁剪节点，并仅用该投影展示当前可见上下级。上级选择器以同一身份的服务端线索查询为候选，只排除当前线索与已返回的可见后代；设置或清除上级始终携带详情 version，成功后更新详情、刷新列表和当前层级缓存。浏览器不补全隐藏节点，也不以本地关系判定循环、容量、字段写权限或数据范围；任何 409 均不自动重试。

## P3 线索状态

线索状态弹层只在详情的 `locked: boolean` 与 `dealStatus: OPEN|WON` 完整可用时开放，避免以遮罩、缺失或未知枚举覆盖服务端字段。锁定与成交状态作为同一 `LeadStateUpdateRequest` 携带原始 version 提交；成功后只以服务端投影更新详情并刷新同一身份列表，409 不自动重试。

## P3 线索关联客户

线索详情的关联客户选择器同时要求 `leads:write` 和 `customers:read`，且只对非 `CONVERTED` 线索显示。候选从同一身份的服务端受限客户目录读取，设置或更换只携带候选 ID 与详情原始 version；清除必须经二次确认，并仅发送生成的 `LeadUpdateRequest.customerId: number | null` 允许的 `customerId: null`。浏览器不从线索、缓存或本地状态推断客户范围、关系有效性、线索状态或字段写权限；服务端仍复核这些条件和并发。

## P3 线索创建前查重

新建线索表单仅在当前成员同时具备 `leads:write` 与 `leads:read` 时提供显式查重操作。它只发送已通过本地格式校验的名称与联系电话，且仅消费服务端当前可见范围内的布尔结果；不会显示、缓存或推断任何潜在重复记录。查重结果只对应最近一次输入，不能替代服务端在创建时的最终校验。

## P3 线索个人关注

详情页的关注/取消关注只调用当前成员的 `PUT /api/v1/leads/{leadId}/star`；该动作只要求线索对当前成员可读，不携带线索 version，也不要求 `leads:write`。服务端成功后才更新当前身份下的详情缓存并失效线索列表缓存；不会改变其他成员的关注状态。

## P3 线索协作者

协作者管理仅在 `leads:assign` 下打开，并按需读取服务端返回的完整 `GET /api/v1/leads/{leadId}/collaborators` 基线。该具名基线包含完整成员、非负 version 与服务端确认的调用者状态；缺失、加载中或解码异常时前端禁用草稿编辑和保存。候选成员只来自同一身份下的服务端可见成员目录；无成员目录读取权限时，仍可调整已加载条目，但不能新增。保存通过 `PUT /api/v1/leads/{leadId}/collaborators` 以该基线 version 替换完整清单；成功后才更新当前身份详情缓存并失效列表与协作者缓存，冲突不自动重试或覆盖草稿。`leads:write` 下的退出协作须明确确认并只提交当前详情 version，服务端决定调用者是否实际可退出。

## P3 线索负责人

负责人变更同时要求 `leads:assign` 与 `organization:read`，候选仅来自当前身份的服务端可见成员目录。提交 `PUT /api/v1/leads/{leadId}/owner` 时携带详情基线 version；成功后才更新当前身份详情和列表缓存。前端不推断成员活跃状态、可分配范围或字段写权限，版本冲突也不自动重试。

## P3 线索删除

详情页仅在服务端明确授予 `leads:delete` 时显示删除确认，并只提交当前详情的 version。成功后移除线索域缓存并返回列表；前端不根据可见层级、转换状态或详情引用判断是否仍有活动下级线索，也不尝试撤回附件或 FILE 字段绑定。服务端独立裁决 owner scope、软删除依赖和并发；409 必须由用户显式选择刷新，不自动重试。

## P3 线索转换

详情页仅对服务端明确为 `ACTIVE` 的线索，在同时拥有 `leads:convert`、`customers:write` 与 `contacts:write` 时显示转换入口。`POST /api/v1/leads/{leadId}/convert` 始终携带当前详情 version 和经过显式填写的客户名称、联系人名称、可选职务；服务端负责原子创建、字段权限、数据范围和乐观锁校验。运行时解码器只保留响应明确返回、且与请求线索一致的线索/客户/联系人 ID 与版本，成功后失效线索缓存；只有相应 read authority 已存在时，才以这些返回 ID 跳转到新建客户或联系人。动态字段映射需要独立的字段访问上下文，当前不会从线索、自定义字段缓存或本地规则推断并提交。

## P3 附近线索

`/crm/leads/nearby` 在 `leads:read` 守卫下，只有用户主动触发浏览器定位后才请求 `GET /api/v1/leads/nearby`。经纬度只保存在页面短生命周期状态和对应的身份隔离 Query Key，不进入 URL、持久化存储、日志或页面展示；半径、页码和每页数量则保留在 URL。首期不接入地图或第三方地图 Key，只按服务端返回的距离排序分页；运行时投影仅保留嵌套线索的既有窄列表字段与非负距离，不能从地址、坐标或缓存推断额外位置数据。

## P3 商机列表

`/crm/opportunities` 以身份键、页码和关键词调用 `POST /api/v1/opportunities/query`，路由和请求均要求 `opportunities:read`。列表运行时只保留服务端返回的名称、客户/负责人 ID 引用、管线/阶段 code、结果、状态和当前成员的关注标识；不读取金额、动态字段、附件、联系人、协作者或地址，也不由客户、成员、导航或缓存推断关联数据的可见性。商机详情、新建与阶段、产品、联系人、协作者动作将使用各自版本化端点另行交付。

## P3 商机详情读取

`/crm/opportunities/:opportunityId` 在 `opportunities:read` 守卫下，以身份隔离 Query Key 读取服务端可见商机。运行时窄投影只保留稳定 ID/version、名称、客户/负责人引用、管线/阶段、基础时间、说明、结果、状态和个人关注标识；金额、联系人、产品、协作者、动态字段与附件均不进入页面或缓存。客户与成员 ID 仅作服务端返回的引用展示，不触发或推断关联对象读取；无效 ID、404 与其他读取失败进入受控状态页。

## P3 商机基础新建

`/crm/opportunities/new` 仅在 `opportunities:write` 下可进入。后端创建时同时要求 `customers:read`，因而客户候选只来自服务端可见客户目录；活动管线与阶段分别来自 `opportunity-pipelines:read` 目录，未取得该目录权限时前端不会猜测或手输 code，而是阻止提交并说明前置条件。首期请求仅含名称、客户 ID、管线 code 和阶段 code，默认负责人保持服务端当前成员；金额、联系人、负责人、协作者、动态字段和 FILE 草稿由独立流程负责。成功后只以服务端返回投影填充当前身份详情缓存并失效列表；没有商机读取权限的创建者只看到成功编号，不会越权跳转详情。

## P3 销售管线目录管理

`/crm/opportunities/pipelines` 仅在 `opportunity-pipelines:read` 下读取身份隔离的租户目录；`OpportunityPipelinePageResponse` 发布一页服务端裁决的管线，选中的服务端管线 ID 再用于 `OpportunityPipelineStagePageResponse` 读取其阶段。运行时窄投影只保留 ID、code、名称、排序、状态、概率和 version，丢弃创建/更新时间；浏览器不从目录推导成员资格、商机记录范围或跨管线阶段。创建、编辑、启停和删除进一步由 `opportunity-pipelines:manage` 守卫，且仅提交当前目录项的服务端 version；服务端仍重验租户目录、父管线、生命周期、依赖和并发。

## P3 商机个人关注

商机详情中的关注开关只向 `opportunities:read` 可见商机的 `/star` 动作提交调用成员的布尔偏好，不带 version、业务字段或其他成员状态。服务端成功后才更新当前身份的详情缓存并失效列表缓存；失败不会乐观写入或推断任何成员偏好。

## P3 商机阶段推进

商机详情只在同时具备 `opportunities:write` 和 `opportunity-pipelines:read` 时显示阶段推进操作。当前管线和候选阶段均来自服务端活动管线目录，浏览器不会手输、推断或跨管线补全 code；请求带详情投影中的原始 version。服务端成功后返回的窄详情投影覆盖当前身份缓存并使列表失效；任何目录、权限或 409 失败都不自动重试或覆盖当前详情。

## P3 商机结果更新

商机详情只为服务端状态为 `ACTIVE` 且具备 `opportunities:write` 的成员提供结果操作。浏览器仅提供后端已定义的结果枚举并带详情原始 version；`OPEN` 不发送说明以恢复跟进，其他结果的说明仅来自用户当前输入。成功响应覆盖当前身份的窄详情缓存并使列表失效；字段权限、商机生命周期和并发始终由服务端复核。

## P3 商机负责人变更

商机详情仅在同时具备 `opportunities:assign` 和 `organization:read` 时提供负责人变更。候选成员来自服务端可见的在职目录，提交只包含候选成员 ID 与详情原始 version；成员可分配范围、字段权限、所有者范围和并发全部由服务端复核，成功后才覆盖当前身份详情缓存并使列表失效。

## P3 商机删除

商机详情仅在 `opportunities:delete` 下显示显式删除确认，并只提交详情原始 version。成功后前端删除当前身份下该商机的详情、关联联系人与关联产品窄投影缓存，使列表失效并返回目录；浏览器不读取、推断或处理客户、联系人、产品、附件或文件字段绑定。所有者范围、软删除、关联撤回与并发均由服务端最终复核，409 不会自动重试。

## P3 商机产品快照

商机详情仅在当前成员同时具有 `opportunities:read` 和 `products:read` 时，以身份隔离 Query Key 请求产品快照。响应缺少稳定 version 或产品 ID/名称时失败关闭；进入缓存和页面的字段仅为名称、编码、分类、单位与数量。list price、unit price、折扣、行金额、总金额及其派生计算一律不进入浏览器。产品整体替换仍等待独立的产品目录与编辑边界；商机协作者替换则等待后端提供完整、可授权读取的协作者基线端点。

## P3 商机联系人与首要联系人

商机详情仅在同时具备 `opportunities:read` 和 `contacts:read` 时，以身份隔离 Query Key 读取服务端可见关联联系人；失败关闭投影只保留联系人 ID、名称和首要标识。此查询会按联系人数据范围裁剪，因而不是全量替换基线，前端绝不据此调用联系人替换端点。设置或清除首要联系人额外要求 `opportunities:write`，选择值只来自该查询结果，请求只含目标 ID（或省略以清除）及详情原始 version；成功响应覆盖详情缓存并失效关联联系人与列表缓存，服务端仍复核字段策略、关联关系、联系人可见性与并发。

## P3 产品列表

`/crm/products` 在 `products:read` 守卫下，以身份隔离 Query Key 发送生成类型的 `POST /api/v1/products/query` 请求；关键词、页码和大小均可由 URL 恢复。由于查询响应在 OpenAPI 中仍为不透明 Pager，运行时窄投影仅保留稳定 ID、名称、编码、分类名称、单位、可用性和状态。价格、负责人、描述、动态字段、附件、版本及其派生值均不进入缓存或页面；字段隐藏、遮罩、范围及搜索可用性继续由服务端复核。

## P3 产品详情读取

`/crm/products/:productId` 在 `products:read` 守卫下以身份隔离 Query Key 读取单个服务端可见产品。运行时投影保留稳定 ID/version、名称、编码、分类名称、单位、目录价、说明、可用性、状态和服务端时间；目录价只格式化服务端数值，浏览器不计算、不缓存为编辑草稿。负责人、动态字段、文件及任何更新请求基线均不进入该详情；无效 ID、404、遮罩导致的无效投影与其他失败都进入受控状态页。

## P3 产品基础新建

`/crm/products/new` 仅在 `products:write` 下可进入，首期请求只提交服务端必填的名称、编码和目录价。目录价受安全 JS number 上限与两位小数输入限制，按用户确认值直接交给生成请求类型；浏览器不做税率、折扣、汇率或其他金额计算。分类、负责人、可用性、说明、动态字段和文件均不猜测或默认填充；成功后只使用服务端返回投影写入当前身份详情缓存并失效列表，有读取权限才跳转详情，否则展示创建编号。

## P3 产品上下架

产品详情仅当服务端返回的可用性为已识别枚举 `AVAILABLE` 或 `UNAVAILABLE`，并且当前身份拥有 `products:write` 时显示上架或下架确认操作。`PUT /api/v1/products/{productId}/availability` 只提交目标枚举和当前详情的原始 version；成功响应覆盖当前身份详情缓存并使列表失效。409 冲突从不自动重试，用户可显式刷新当前详情后保留或放弃尚未提交的目标状态；完整产品编辑仍不使用详情投影拼装请求。

## P3 产品负责人

产品详情仅在同时具备 `products:assign` 与 `organization:read` 时读取服务端成员目录并提供负责人变更。候选严格限于目录返回的在职成员，浏览器不会从当前身份、详情投影或其他业务对象推断负责人；`PUT /api/v1/products/{productId}/owner` 只提交所选 actor ID 与当前详情原始 version。成功响应覆盖详情缓存并使列表失效；409 必须由用户显式刷新，不能自动重试或覆盖。

`DELETE /api/v1/products/{productId}` 仅在 `products:delete` 下以二次确认触发，并只提交详情原始 version。成功后移除该详情缓存、使列表失效并返回目录；前端不尝试管理产品可用性、附件或文件字段，服务端负责软删除、下架及撤回绑定。409 只能显式刷新详情后再次确认。

## P3 产品分类树与节点维护

`/crm/products/categories` 在 `products:read` 下读取服务端分类树。由于快照将分类成功响应标为 opaque，浏览器使用有深度上限的窄运行时解码器，只保留 ID、父级 ID、名称、状态、版本与子节点；任何无效节点都会使查询进入受控错误状态。`products:write` 可创建根节点，或从当前服务端树选择父节点创建子分类；请求仅发送名称及该节点 ID，不接受 URL、手输值或本地推断的父级。重命名提交新名称、原始 version 与树返回的父级 ID；移动则保留树返回的名称，提交目标父级和原始 version。移动候选排除当前父级、自身及全部后代，子节点可明确移动到根级；409 要求用户显式刷新后使用新版本。`products:delete` 下的删除必须二次确认，只发送节点原始 version；浏览器不猜测子节点或产品依赖，服务端继续复核，409 刷新后需再次确认。

## P3 联系人详情读取

联系人名称只进入 `/crm/contacts/:contactId` 的受 `contacts:read` 守卫详情页。详情查询与列表缓存按身份隔离，运行时投影明确排除 `customFields` 和 `fileFields`；无效 ID、404 与其他读取异常都进入受控状态页。已返回的客户和负责人 ID 仅作引用展示，不触发或推断关联对象查询。

## P3 联系人新建

`/crm/contacts/new` 仅在服务端返回 `contacts:write` 时显示入口并允许进入。基础表单使用生成的 `ContactCreateRequest`，空的可选输入不会伪装成业务字段更新；创建成功后只失效联系人列表并填充新记录详情缓存。负责人、关联客户、上级联系人、协作者、地址、标签、动态字段和 FILE 草稿都要等具备独立的可见性约束选择器或状态机后才会进入表单。

## P3 联系人基础编辑

`/crm/contacts/:contactId/edit` 只在 `contacts:write` 可用时访问，更新请求仅携带变动的名称、职务、联系方式、邮箱、网站、说明和下次联系时间，并携带加载时的 version。下次联系时间从详情转换为本地日期时间控件值，只有用户修改才发送；清空时以生成契约的 `null` 明确表达，未修改则保持省略。已审阅的 409 冲突通过显式的刷新/丢弃决策处理，绝不自动重试。关联客户、地址、动态字段和 FILE 字段仍保留为独立受可见性约束流程。

## P3 联系人创建前查重

新建联系人表单提供明确的“检查重复”动作，只提交本地格式校验通过的名称和联系电话。服务端仅返回成员可见范围内的布尔结果，前端既不显示也不缓存任何匹配联系人；结果只对应最近一次输入，不能代替创建时的服务端最终校验。

## P3 联系人个人关注

联系人详情的关注只调用 `PUT /api/v1/contacts/{contactId}/star`，该接口按 `contacts:read` 和当前可见性更新调用成员的个人状态，不需要联系人写权限。成功后仅更新该身份下的详情缓存并失效联系人列表；不会改变其他成员的关注状态或联系人 version。

## P3 联系人关联客户

联系人详情的关联客户选择器必须同时拥有 `contacts:write` 和 `customers:read`，候选客户从服务端可见范围查询，保存时通过联系人更新接口携带联系人 version 和选中客户 ID。浏览器不依据联系人权限推断客户可见性；当前已依据生成的 `ContactUpdateRequest.customerId: number | null` 契约提供明确确认的清除操作，且仅发送 `customerId: null` 与详情原始 version，服务端仍复核字段写权限、客户关系和并发。

## P3 联系人层级

联系人详情读取 `GET /api/v1/contacts/{contactId}/hierarchy` 所返回的受数据范围裁剪的节点，并只用这些节点展示当前可见上下级。上级选择器排除当前联系人及服务端已返回的可见后代，仍由后端拒绝循环与容量超限；设置或清除上级始终携带 version，成功后失效当前身份的层级缓存。

## P3 联系人状态

联系人状态弹层只在详情的 `locked: boolean` 与 `dealStatus: OPEN|WON` 完整可用时开放，锁定和成交状态以同一生成请求及原始 version 提交。浏览器不从标签、客户、负责人、生命周期或缓存推断状态/字段写权限；成功响应覆盖详情、刷新列表，409 不自动重试。

## P3 联系人协作者

联系人协作者的读取与完整替换均以 `contacts:assign` 作为 UI 防护，并以服务端 `GET /api/v1/contacts/{contactId}/collaborators` 返回的完整列表作为替换基线。任何不完整或异常响应都会禁止保存，避免前端误删不可见协作者；新增候选还要求 `organization:read`，最终在职状态、成员范围、读写权限与乐观锁均由服务端复核。

## P3 联系人负责人

联系人负责人变更以 `contacts:assign` 与 `organization:read` 共同守卫，候选项只来自服务端在职成员列表。`PUT /api/v1/contacts/{contactId}/owner` 始终携带当前 version，成功后更新身份隔离的详情缓存并失效列表；成员可见范围和最终负责人可分配性均由服务端裁决。

## P3 联系人删除

详情页仅在服务端明确授予 `contacts:delete` 时显示删除确认，并只提交当前详情的 version。成功后移除联系人域缓存、失效公海缓存并返回列表；前端不根据可见层级判断是否仍有活动下级联系人，也不尝试撤回附件或 FILE 字段绑定。服务端独立裁决 owner scope、软删除依赖和并发；409 必须由用户显式选择刷新，不自动重试。

## P3 联系人 CSV 导出

联系人导出仅在 `contacts:export` 下提供入口，并通过受控 `POST /api/v1/contacts/export/csv` 获取 Blob。当前只提交列表 URL 中的关键词及固定的 `contact_name` 字段；浏览器不读取、拼接或改写 CSV，服务端负责导出与读取范围交集、字段未遮罩访问和文件内容。

## P3 联系人公海目录

`/crm/contact-pools` 仅使用 `GET /api/v1/contact-pools/catalog`，而不是要求 `contact-pools:manage` 的配置查询接口。目录缓存带入身份键，并以窄解码器保留服务端返回的 ID、名称、状态、联系人计数与当前成员管理员标识；成员资格、公海范围和联系人可见性都不在浏览器重算。联系人列表、领取、分配和删除将按各自 endpoint 与独立 authority 继续交付。

## P3 联系人公海联系人列表

公海联系人页面先用同一身份隔离的 catalog 确认该 `poolId` 已由服务端列为当前成员可访问，再查询 `GET /api/v1/contact-pools/{poolId}/contacts`。页码、大小和名称搜索保留在 URL；列表仅使用公海 endpoint 返回的字段投影。即使当前成员同时拥有 `contacts:read`，跳转到全局联系人详情也只是该 authority 已显式授予时的可选入口，不能从公海读取权限推导。

## P3 联系人移入公海

联系人详情仅在服务端明确返回 `ACTIVE` 状态、且前端同时持有 `contacts:write`、`contact-pools:read` 与 `contact-pools:release` 时提供单条移入入口。候选公海只来自 catalog 的启用项；提交只带当前联系人的 ID 和 version。成功后失效联系人与公海缓存，并进入目标公海列表；任何 409 都交由已审阅的冲突提示处理，不会自动重试或替换 version。

## P3 联系人领取公海

公海联系人列表使用仅限该 endpoint 的窄投影保留服务端版本号；在联系人仍为 `IN_POOL` 且服务端 authorization 含 `contact-pools:claim` 时才显示单条领取。提交只带列表响应的联系人 ID/version；领取成功后失效当前身份的联系人列表与公海缓存。领取上限、原负责人冷却、成员资格、启用状态、数据范围和并发冲突都由服务端最终裁决，前端不会重试 409 或用本地规则预判可领取性。

## P3 联系人公海分配

联系人公海管理员在拥有 `contact-pools:assign` 时可对仍在池内的单条联系人打开分配器；管理员标识只来自 catalog，候选成员只来自 `organization:read` 所允许的在职成员目录。提交带选中成员 ID 与公海列表响应的联系人 ID/version；成功后失效当前身份的联系人列表与公海缓存。浏览器不判断目标成员是否最终可分配，也不绕过服务端对管理员、启用状态、成员在职、数据范围及并发版本的校验。

## P3 联系人从公海删除

联系人公海管理员在拥有 `contact-pools:delete` 时可对仍在池内的单条联系人发起明确确认的软删除。提交只带公海列表响应的联系人 ID/version；成功后失效当前身份的联系人列表与公海缓存。子联系人存在性、管理员资格、池内归属、附件与 FILE 撤回、软删除状态和并发版本由服务端裁决；前端不会将“从公海删除”伪装成普通移出或自动重试冲突。

## P3 联系人公海配置列表

`/crm/contact-pools/manage` 仅在 `contact-pools:manage` 下读取管理分页接口；其独立的窄投影保留配置清单展示所需的版本、状态、成员范围、领取规则和服务端统计。该页面不从 catalog 或本地身份推导配置权限，目录中的管理入口只作为额外 UI 防护；管理接口、路由守卫与服务端均会再次裁决。

## P3 联系人公海基础创建

管理列表在 `contact-pools:manage` 下提供基础创建。管理员候选只来自 `organization:read` 的服务端在职成员目录；首期提交名称、已选管理员，并将该显式选择同步为最小的成员资格范围，以满足服务端公海至少需要一个可领取成员或部门的契约。其余默认值为无限制日领取、零天原负责人冷却、关闭自动释放和空规则。部门、额外资格成员、自动释放和规则的精细配置将随独立编辑流程交付。

## P3 联系人公海状态切换

管理清单仅在服务端响应明确标记当前成员为管理员时显示启停入口，并提交当前配置行的 ID/version 与目标状态。停用有联系人的公海会被前端提示为不可用，但该联系人计数和管理员资格都只用于体验防护；服务端仍会复核 `contact-pools:manage`、当前管理员、乐观锁与公海是否为空。状态变更后统一失效公海缓存，不做本地状态推测；版本或并发冲突必须由用户明确点击“刷新状态”后重新读取。

## P3 联系人公海基础配置编辑

管理员可编辑名称、管理员范围、日领取上限、原负责人冷却期、自动释放规则以及领取成员/部门范围。管理员、成员与部门候选只能来自 `organization:read` 的服务端目录，现有范围仅从管理投影回显；浏览器不从本地身份、权限或缓存推断引用。新增管理员会同步加入领取成员范围，编辑器至少保留一名管理员和一名领取成员或一个部门范围。自动释放启用时，浏览器要求至少一条由服务端枚举限定的规则。更新只携带打开编辑器时的 version，成功后失效公海缓存。若发生版本或并发冲突，用户可选择保留草稿并锁定它，或放弃草稿后刷新；不会自动重试或以新版本覆盖旧草稿。

## P3 联系人公海整池转移

管理列表仅对服务端明确标记为当前成员管理员且仍有联系人的来源公海显示转移入口。目标只从同一 `contact-pools:manage` 管理接口返回的分页清单中选择，并在 UI 中筛为非来源、启用的公海；浏览器只提交目标 ID，不伪造版本或本地搬迁结果。确认后服务端锁定两个公海、复核来源管理员资格与目标启用状态，再原子转移成员关系；成功后失效所有公海缓存。并发冲突不会自动重试，用户可显式刷新后重新确认。

## P3 联系人公海删除

管理列表仅对服务端明确标记为当前成员管理员的条目提供删除操作，并以当前管理投影的联系人数量做体验防护；有联系人的公海必须先转移或处理联系人。确认删除只携带来源管理投影的 ID/version，成功后失效所有公海缓存。服务端在删除时重新锁定公海、校验管理员和 version、确认联系人确为空，并负责自动释放配置的同步；409 冲突只能显式刷新状态，绝不自动重试。

## P2 动态字段展示核心

动态字段响应通过一个窄的运行时展示投影解码：仅保留字段 code、显示名称、类型、状态、排序、分组、可搜索性和选项。未知字段类型、重复 code 或不合法选项会被忽略，非数组的字段定义响应与不完整布局响应会以受控错误失败；不会把后端 DTO 复制到前端。字段定义和成员布局的 Query Key 必须同时带入 identity、object type 与来自服务端 authorization bootstrap 的不透明 access context，后者只用于隔离缓存，绝不可作为前端授权依据。

`DynamicFieldDisplay` 的 effective access 只能由已获服务端许可的上下文显式传入。`HIDDEN` 与 `FULL` 遮罩在组件最先返回，绝不读取或输出传入值；`PARTIAL` 只展示服务端已遮罩的原值，前端不拼接历史值或自行复原。FILE 字段只显示受控的数量摘要，受保护文件内容仍须经 blob 下载通道。

## 安全基线

开发身份 Header 仅可通过开发 AuthAdapter 在 `import.meta.env.DEV` 显式启用，身份值仅放在 `sessionStorage`。生产包不得存在该 Adapter 或 Header 配置。附件下载和预览在生产认证与短时 URL/同源 Cookie 方案定案前一律用受控 fetch + blob，不使用直连受保护资源的 URL。

字段元数据与查询缓存必须以 tenant、actor、object type 和权限上下文隔离；任一身份或 tenant 变化都必须清空缓存与未完成页面状态。遮罩值不能与历史值拼接、缓存或推断。
